# 6-digit login codes

## Situation

The code in the email is generated by the backend auth service, not by our app. Our email template just prints the token it receives (`payload.data.token`), and the login screen verifies it with the auth service. The backend's OTP length is currently 8 and there is no setting exposed to this project to change it to 6 — the auth configuration surface available here covers signup, confirmation, password and rate-limit options only.

So making codes 6 digits means issuing our own code instead of relying on the built-in one.

## Recommended approach: app-issued 6-digit codes

We already have this exact machinery for override codes: a server function validates a code, mints a one-time login link server-side, and the browser exchanges it for a session. We reuse that pattern for email sign-in.

Flow:

```text
Captain enters email
  -> server fn: create 6-digit code, store hash + expiry, send email
Captain enters 6 digits in the app
  -> server fn: verify code, mint login link server-side
  -> browser exchanges it -> signed in -> /captain
```

Rules to enforce server-side:
- 6 digits, single-use, 10-minute expiry
- Max 5 verify attempts per code, then invalidate
- Rate limit: 1 send per 30s and 5 sends per hour per email
- Codes stored hashed, never returned to the client

## What changes

- New table for login codes (email, code hash, expires_at, attempts, used_at), RLS locked to no client access, plus grants for the service role only.
- New server functions in `src/lib/captain.functions.ts`: `requestLoginCode` and `verifyLoginCode`, verify path mirroring the existing override-code redemption (provision the account if the email is a registered captain, mint link, return token hash).
- Email sending reuses the existing custom email queue/route so the message keeps the current branding; the magic-link template gets a variant that renders the 6-digit code (and the tap-to-open link).
- `src/routes/login.tsx`: OTP length 8 -> 6, and the captain tab calls the two new server functions instead of `signInWithOtp` / `verifyOtp`.
- Tests in `src/lib/__tests__/captain.functions.test.ts` for expiry, wrong code, attempt lockout, reuse, and unknown email.

## Trade-off

This adds a small amount of auth code we own rather than leaning entirely on the built-in flow. The security-sensitive parts (session minting, account provisioning) still go through the auth service exactly as the override flow does today. If you'd rather not own that, the alternative is keeping 8-digit codes as-is.
